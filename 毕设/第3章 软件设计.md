# 第3章 软件设计

软件设计承接第 2 章需求分析，在明确"系统要做什么"之后，回答"系统如何组织与分解"的问题。本章首先给出平台的总体体系结构与技术选型，说明前后端分离与微服务拆分原则；随后从功能视角对系统进行模块划分。功能模块的组织方式参照常见的分层思路——核心业务办理、业务记录与监管、多媒体与凭证上报、远程管理端、基础主数据维护——对应到本课题即为订单交易与履约、订单与资金监管、文件与上传、管理端与实时通讯、游戏与权限等子模块。各节给出模块职责、关键协作关系及与微服务、前后端工程的对应关系，并预留总体功能结构图供排版插入。

## 3.1 软件体系结构设计

### 3.1.1 设计目标与原则

本系统面向发单用户、代练人员与后台运营人员，业务上存在订单撮合、资金托管、即时沟通与后台监管等并发与一致性要求。体系结构设计遵循以下原则：

（1）**前后端分离**【10】：用户端（`game-boosting-platform-ui`）与管理端（`game-boosting-platform-admin-ui`）独立构建与部署，通过 HTTPS 调用统一网关暴露的 RESTful API，降低展示层与业务层的耦合，便于多端扩展与迭代。

（2）**微服务拆分与单一职责**【11】：按业务域将后端划分为用户、订单、账户、文件、AI、WebSocket 等可独立部署的服务单元，每个服务围绕明确边界组织领域逻辑，避免"单体巨石"带来的扩展与发布风险。

（3）**统一接入与安全**：外部请求经 API 网关（`jmz-gateway`）统一路由、限流与鉴权入口，配合安全模块（`jmz-security`）与 JWT 机制【9】，实现跨服务的一致认证授权策略。

（4）**基础设施可替换**：服务注册与配置依托 Nacos【7】；持久化采用 MySQL【18】；热点与会话元数据采用 Redis【17】；非结构化文件交由阿里云 OSS【16】；服务间同步调用采用 Spring Cloud OpenFeign。上述组件均可按部署环境替换或伸缩。

### 3.1.2 总体逻辑架构

系统在逻辑上可分为四层。

**（1）表现层。** 用户端基于 Vue 3、Element Plus、Pinia 等实现订单发布、接单、聊天、账户等前台功能；管理端同样基于 Vue 3 体系实现游戏数据、订单监管、RBAC、账户调账等运营功能。表现层仅负责交互、校验与接口编排，不直接访问数据库。

**（2）接入层。** `jmz-gateway` 作为 B/S 架构下的统一入口，完成路由转发、跨域与安全相关的前置处理，将请求分发至各业务微服务。

**（3）业务服务层。** 各微服务承载领域逻辑：`server-user` 负责用户、菜单、权限、游戏基础数据等；`server-order` 负责订单状态机、异常单与介入处理等；`server-account` 负责账户余额、冻结解冻、充值提现及与支付宝等渠道的对接；`jmz-file` 负责上传凭证与对象存储对接；`server-ai` 封装大语言模型调用，提供定价建议、文案优化与接单推荐；`server-websocket` 提供消息通讯与订单相关推送能力。公共能力沉淀在 `jmz-common` 各子模块（如核心工具、MyBatis-Plus、Redis、Feign、安全域对象等）。

**（4）数据与基础设施层。** MySQL 存储业务主数据与事务型数据；Redis 支撑缓存与 WebSocket 会话路由等；OSS 存储图片与附件；Nacos 维护服务实例与动态配置。

上述分层与第 1 章所述技术路线一致，可概括为"双前端 + 网关 + 多微服务 + 统一数据与中间件"的体系结构。

## 3.3 数据库设计
### 3.3.1 实体类关系分析

实体类关系图是用来表示系统中各个实体类之间及其属性关联关系的图。由于用户管理缩略类图涉及用户信息、角色信息和权限信息；账户管理缩略类图涉及账户信息和流水信息；代练管理缩略类图涉及订单信息和订单状态日志信息；消息通讯缩略类图涉及消息信息；文件管理缩略类图涉及文件信息；游戏管理缩略类图涉及游戏信息、游戏系统信息和区服信息。因此，游戏代练平台包括用户信息、账户信息、订单信息、消息信息、流水信息、游戏信息、游戏系统信息、区服信息、角色信息、权限信息和菜单信息共十一个实体类。
图 3-8 实体类关系设计

如图 3-8 所示，订单信息是平台的核心实体，一个用户可以选择多个代打游戏，一个游戏可以被多个用户选择代打，故用户信息与游戏信息是多对多的关联关系（通过用户代打游戏关联表维护）；一个用户可以拥有一个账户信息，故用户信息与账户信息是一对一的关联关系；一个用户可以拥有多个角色，一个角色可以对应多个用户，故用户信息与角色信息是多对多的关联关系；一个用户可以发布多条消息，故用户信息与消息信息是一对多的关联关系；一个用户可以发布多个订单，故用户信息与订单信息是一对多的关联关系（订单的发布者、接手者、介入客服均关联至用户信息）。一个账户属于一个用户，故账户信息与用户信息是一对一的关联关系；一个账户可以产生多条流水记录，故账户信息与流水信息是一对多的关联关系。一条流水关联一个用户和一笔订单（可选），故流水信息与用户信息是一对多的关联关系，流水信息与订单信息是一对多的关联关系。一个订单关联一个游戏信息、一个游戏系统信息和一个游戏服务区信息，故订单信息与游戏信息、订单信息与游戏系统信息、订单信息与游戏服务区信息均是多对一的关联关系；一个订单可以产生多条消息记录，故订单信息与消息信息是一对多的关联关系。一个游戏可以对应多个系统信息和多个区服信息，故游戏信息与游戏系统信息、游戏信息与游戏服务区信息均是一对多的关联关系。一个系统可以关联多个游戏和多个区服，故游戏系统信息与游戏信息是多对一的关联关系，游戏系统信息与游戏服务区信息是一对多的关联关系。一个区服关联一个游戏和一个系统，故游戏服务区信息与游戏信息、游戏服务区信息与游戏系统信息均是多对一的关联关系。一个角色可以绑定多个菜单，故角色信息与菜单信息是一对多的关联关系；一个角色可以拥有多个权限，故角色信息与权限信息是一对多的关联关系。一条消息关联一个发送者用户和一个接收者用户（可选），同时可关联一个订单，故消息信息与用户信息是一对多的关联关系（发送者），消息信息与用户信息是一对多的关联关系（接收者），消息信息与订单信息是一对多的关联关系。菜单信息用于存储系统左侧菜单栏配置数据，支持树形层级结构，一个菜单可以包含多个子菜单，故菜单信息内部存在一对多的自关联关系。

### 3.3.2 逻辑模型设计

数据库逻辑设计的任务是将概念结构转换成特定DBMS所支持的数据模型的过程。关系数据库逻辑设计的结果是一组关系模式的定义。

根据游戏代练平台概念模型可以转换为如下逻辑模型：

用户信息（用户ID，用户名，手机号，密码，邮箱，头像，昵称，性别，状态，创建时间，更新时间，是否开启代练）；
账户信息（账户ID，用户ID，余额，创建时间，更新时间）；
订单信息（订单ID，发布者ID，接手者ID，客服ID，游戏ID，系统ID，区服ID，接单账号，订单类型，代练内容，要求段位，当前段位，目标段位，价格，完成时间，订单状态，创建时间，更新时间）；

role_id是表3-16角色菜单关联表的外键，引用tb_jmz_role表的id字段；menu_id是表3-16角色菜单关联表的外键，引用tb_jmz_menu表的id字段；role_id与menu_id共同构成表3-16的联合主键，实现角色与菜单的多对多绑定，支撑管理端动态菜单渲染与权限控制。
