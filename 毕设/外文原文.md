## 原文片段

### Abstract

WebSocket compression allows reducing the size of messages exchanged between a client and server over a WebSocket connection. It is achieved using the permessage-deflate algorithm (see RFC 7692), which compresses the data before transmission. By reducing the data size, WebSocket compression helps optimize bandwidth usage and may actually lower latency due to the reduced data size over the wire.

However, enabling WebSocket compression in high-concurrency scenarios introduces significant CPU and memory overhead. When broadcasting to channels with many online subscribers, the compression operation is executed concurrently for each connection, resulting in a heavy load on sync.Pool and temporary memory spikes. This paper describes a PreparedMessage caching optimization that significantly reduces memory allocations and CPU utilization during broadcasts, while preserving the bandwidth savings of WebSocket compression. Benchmark results demonstrate that the PreparedMessage approach reduces broadcast latency by up to 4x and memory allocations by over 90% in high-concurrency scenarios.

### 1. Introduction

Real-time messaging systems built with WebSocket often face a critical trade-off: bandwidth cost versus server resource consumption. For applications pushing high-frequency updates to thousands of concurrent subscribers, enabling WebSocket compression via the permessage-deflate extension (RFC 7692) can reduce transmit bandwidth by up to 3x. This translates to substantial cost savings — in one production case, a customer reduced bandwidth usage from 45 MiB/s to 15 MiB/s across all nodes, saving approximately $12,000 per month.

However, the benefits come at a cost. Enabling compression causes approximately a 2x increase in CPU usage and sporadic memory spikes up to 2.5x larger than baseline values. The root cause lies in how WebSocket libraries handle compression: each message broadcast requires compressing the same payload independently for every recipient connection, creating redundant work and memory pressure on sync.Pool.

This paper presents a PreparedMessage caching technique that eliminates redundant compression operations. The optimization is now part of the open-source centrifugal/centrifuge library for Go and the Centrifugo PRO offering, but the concepts are applicable to any WebSocket server implementation.

### 2. Background: WebSocket Compression and the Problem

#### 2.1 Permessage-Deflate Extension

WebSocket compression is implemented using the permessage-deflate algorithm specified in RFC 7692. In Go implementations using the Gorilla WebSocket library, compression is enabled by setting the EnableCompression option on the websocket.Upgrader:

```go
var upgrader = websocket.Upgrader{
    EnableCompression: true,
}
```

Individual messages can then be compressed using the EnableWriteCompression method:

```go
conn.EnableWriteCompression(true)
conn.WriteMessage(websocket.TextMessage, data)
```

The Gorilla WebSocket library uses Go's standard compress/flate package for compression, maintaining separate sync.Pool instances for each compression level (1–9). This pooling strategy reduces allocations by reusing flate.Writer and flate.Reader objects.

#### 2.2 The Performance Problem

In PUB/SUB patterns common to real-time messaging, a single message published to a channel may need to be delivered to thousands of online subscribers simultaneously. With compression enabled, each delivery requires:

1. Acquiring a flate.Writer from sync.Pool (approximately 650 KB per object)
2. Compressing the same message payload independently
3. Writing the compressed frame to the connection
4. Releasing the writer back to the pool

For a broadcast to 10,000 concurrent subscribers, this results in:
- 10,000 independent compression operations of identical data
- sync.Pool growing significantly during peak broadcast periods
- Memory spikes up to 2.5x normal usage
- CPU utilization approximately 2x higher than without compression

### 3. The PreparedMessage Optimization

#### 3.1 Concept

The Gorilla WebSocket library provides a PreparedMessage type that caches the on-the-wire representation of a message payload. Instead of compressing a message for each connection, the message is compressed once and the resulting frame is reused across all connections.

```go
// PreparedMessage caches on the wire representations of a message payload.
// Use PreparedMessage to efficiently send a message payload to multiple
// connections. PreparedMessage is especially useful when compression is used
// because the CPU and memory expensive compression operation can be executed
// once for a given set of compression options.
type PreparedMessage struct {
    messageType int
    data        []byte
    mu          sync.Mutex
    frames      map[prepareKey]*preparedFrame
}
```

#### 3.2 Implementation

The optimization works by creating a PreparedMessage once per unique payload, then reusing it for all target connections:

```go
preparedMessage, _ := websocket.NewPreparedMessage(websocket.TextMessage, data)
for _, conn := range subscribers {
    conn.WritePreparedMessage(preparedMessage)
}
```

For the Centrifuge library, a PreparedMessage cache is maintained within the WebSocket transport layer. The cache uses the message payload as the key and stores PreparedMessage objects with a short TTL (approximately 1 second). This avoids introducing WebSocket-specific types into the PUB/SUB broadcasting layer.

```go
cache := otter.MustBuilder[string, *websocket.PreparedMessage](
    int(config.CompressionPreparedMessageCacheSize),
).Cost(func(key string, value *websocket.PreparedMessage) uint32 {
    return 2 * uint32(len(key))
}).WithTTL(time.Second).Build()
```

#### 3.3 Benchmark Results

Benchmarks demonstrate the significant performance improvement of the PreparedMessage approach:

| Scenario | Without PreparedMessage | With PreparedMessage | Improvement |
|----------|------------------------|---------------------|-------------|
| 100 connections | 198,619 ns/op, 14,113 B/op, 301 allocs | 42,643 ns/op, 12,320 B/op, 19 allocs | ~4.7x faster, ~95% fewer allocs |
| 1,000 connections | 1,797,432 ns/op, 123,864 B/op, 3,001 allocs | 649,506 ns/op, 11,421 B/op, 19 allocs | ~2.8x faster, ~99% fewer allocs |
| 10,000 connections | 16,506,132 ns/op, 1,040,709 B/op, 30,007 allocs | 7,702,265 ns/op, 11,631 B/op, 21 allocs | ~2.1x faster, ~99% fewer allocs |

The impact becomes more significant as the number of concurrent connections increases. At 10,000 connections, the PreparedMessage approach reduces memory allocations from 30,007 to just 21 per broadcast operation.

### 4. Related Work: Scaling WebSockets to Millions of Connections

Beyond compression optimization, production WebSocket systems require careful architectural design to handle massive scale. According to WebSocket.org's guide on scaling WebSocket architectures, the following patterns are essential:

**Pub/Sub Backplane**: Use Redis, Kafka, or NATS as a message broker between WebSocket server instances. When a message needs to reach clients on different servers, publish it to the backplane and let each server fan out to its local connections. This decouples servers from each other and enables horizontal scaling.

**Connection Management**: Each WebSocket server can manage 500,000–1,000,000 concurrent connections using event-driven I/O (epoll on Linux). With 50 million concurrent connections, approximately 50–100 WebSocket servers are needed. Store user-to-server mappings in Redis so any instance can handle reconnections.

**Load Balancing**: Use Layer 4 load balancing with least-connection algorithms for WebSocket traffic. Sticky sessions are a pragmatic starting point at moderate scale; for higher scale, externalize session state to Redis so any server can handle any reconnecting client.

---

### 5. Conclusion

This paper presented a PreparedMessage caching optimization for WebSocket compression in high-concurrency real-time messaging systems. The optimization eliminates redundant compression operations by caching compressed WebSocket frames and reusing them across multiple connections. Benchmark results demonstrate up to 4x reduction in broadcast latency and over 90% reduction in memory allocations at high concurrency levels.

Combined with architectural patterns such as Redis Pub/Sub for cross-node communication and external session state management, these optimizations enable WebSocket servers to efficiently handle hundreds of thousands to millions of concurrent connections while maintaining low latency and controlled resource consumption.

The optimization is production-ready and available as part of the open-source centrifugal/centrifuge library for Go.
