## 中文译文

### WebSocket压缩性能优化的Go应用实践

**摘要**

WebSocket压缩通过减少客户端与服务器之间传输的消息大小来优化带宽使用。目前，这一功能通过RFC 7692规定的permessage-deflate算法实现，在传输前对数据进行压缩。通过减小数据大小，WebSocket压缩有助于优化带宽使用，并且由于线路上传输的数据量减少，实际上还可能降低延迟。

然而，在高并发场景下启用WebSocket压缩会带来显著的CPU和内存开销。当向拥有大量在线订阅者的频道进行广播时，压缩操作需要为每个连接独立执行，导致sync.Pool负载激增和临时内存峰值。本文介绍了一种PreparedMessage缓存优化技术，该技术显著减少了广播过程中的内存分配和CPU利用率，同时保留了WebSocket压缩的带宽节省优势。基准测试结果表明，在高并发场景下，PreparedMessage方法将广播延迟降低了最多4倍，内存分配减少了90%以上。

**关键词**：WebSocket；实时通信；性能优化；消息压缩；连接管理；高并发

---

### 1 引言

基于WebSocket构建的实时消息系统经常面临一个关键的权衡：带宽成本与服务器资源消耗。对于需要向数千个并发订阅者推送高频更新的应用程序，通过permessage-deflate扩展（RFC 7692）启用WebSocket压缩可将传输带宽减少多达3倍。这带来了可观的成本节省——在一个生产案例中，某客户将跨所有节点的带宽使用量从45 MiB/s降低到15 MiB/s，每月节省约12,000美元。

然而，这些好处是有代价的。启用压缩会导致CPU使用率增加约2倍，内存峰值最高达到基线的2.5倍。根本原因在于WebSocket库处理压缩的方式：每条消息广播都需要为每个接收方连接独立压缩相同的有效载荷，造成冗余工作和内存压力。

本文提出了一种PreparedMessage缓存技术，通过缓存压缩后的WebSocket帧并在所有连接中重复使用，消除了冗余的压缩操作。该优化现已成为Go语言的centrifugal/centrifuge开源库和Centrifugo PRO产品的一部分，但这些概念适用于任何WebSocket服务器实现。

---

### 2 背景：WebSocket压缩与性能问题

#### 2.1 Permessage-Deflate扩展

WebSocket压缩使用RFC 7692规定的permessage-deflate算法实现。在使用Gorilla WebSocket库的Go实现中，通过在websocket.Upgrader上设置EnableCompression选项来启用压缩：

```go
var upgrader = websocket.Upgrader{
    EnableCompression: true,
}
```

然后可以使用EnableWriteCompression方法对单个消息进行压缩：

```go
conn.EnableWriteCompression(true)
conn.WriteMessage(websocket.TextMessage, data)
```

Gorilla WebSocket库使用Go标准库的compress/flate包进行压缩，为每个压缩级别（1-9）维护独立的sync.Pool实例。这种池化策略通过重复使用flate.Writer和flate.Reader对象来减少分配。

#### 2.2 性能问题

在实时消息系统中常见的发布/订阅模式中，发布到频道的单条消息可能需要同时传递给数千个在线订阅者。启用压缩后，每次传递都需要：

1. 从sync.Pool获取flate.Writer（每个对象约650 KB）
2. 为每个连接独立压缩相同的消息有效载荷
3. 将压缩帧写入连接
4. 将writer释放回池

对于向10,000个并发订阅者的广播，这导致：
- 10,000次相同数据的独立压缩操作
- sync.Pool在峰值广播期间显著增长
- 内存峰值达到正常用量的2.5倍
- CPU利用率比不压缩时高约2倍

### 3 PreparedMessage优化技术

#### 3.1 概念

Gorilla WebSocket库提供了PreparedMessage类型，用于缓存消息有效载荷的在线表示形式。消息只需压缩一次，生成的帧即可在所有目标连接中重复使用。

```go
// PreparedMessage缓存消息有效载荷的在线表示形式。
// 使用PreparedMessage可高效地将消息有效载荷发送到多个连接。
// PreparedMessage在启用压缩时特别有用，因为CPU和内存密集的压缩操作
// 可以对一组给定的压缩选项仅执行一次。
type PreparedMessage struct {
    messageType int
    data        []byte
    mu          sync.Mutex
    frames      map[prepareKey]*preparedFrame
}
```

#### 3.2 实现

该优化通过为每个唯一的有效载荷创建一次PreparedMessage，然后将其重复用于所有目标连接来实现：

```go
preparedMessage, _ := websocket.NewPreparedMessage(websocket.TextMessage, data)
for _, conn := range subscribers {
    conn.WritePreparedMessage(preparedMessage)
}
```

对于Centrifuge库，在WebSocket传输层维护PreparedMessage缓存。缓存使用消息有效载荷作为键，存储带有短TTL（约1秒）的PreparedMessage对象。这避免了在PUB/SUB广播层引入WebSocket特定类型。

```go
cache := otter.MustBuilder[string, *websocket.PreparedMessage](
    int(config.CompressionPreparedMessageCacheSize),
).Cost(func(key string, value *websocket.PreparedMessage) uint32 {
    return 2 * uint32(len(key))
}).WithTTL(time.Second).Build()
```

#### 3.3 基准测试结果

基准测试证明了PreparedMessage方法的显著性能改进：

| 场景 | 无PreparedMessage | 使用PreparedMessage | 改进 |
|------|------------------|-------------------|------|
| 100个连接 | 198,619 ns/op, 14,113 B/op, 301次分配 | 42,643 ns/op, 12,320 B/op, 19次分配 | 快约4.7倍，分配减少约95% |
| 1,000个连接 | 1,797,432 ns/op, 123,864 B/op, 3,001次分配 | 649,506 ns/op, 11,421 B/op, 19次分配 | 快约2.8倍，分配减少约99% |
| 10,000个连接 | 16,506,132 ns/op, 1,040,709 B/op, 30,007次分配 | 7,702,265 ns/op, 11,631 B/op, 21次分配 | 快约2.1倍，分配减少约99% |

随着并发连接数量的增加，影响变得更加显著。在10,000个连接时，PreparedMessage方法将每次广播操作的内存分配从30,007次减少到仅21次。

### 4 扩展工作：将WebSocket扩展到数百万连接

除了压缩优化外，生产级WebSocket系统还需要精心的架构设计来处理大规模部署。根据WebSocket.org关于扩展WebSocket架构的指南，以下模式至关重要：

**发布/订阅后端**：使用Redis、Kafka或NATS作为WebSocket服务器实例之间的消息代理。当消息需要到达不同服务器上的客户端时，将其发布到后端，让每台服务器将其扇出到本地连接。这解耦了服务器之间的耦合，实现了水平扩展。

**连接管理**：使用事件驱动I/O（Linux上的epoll），每台WebSocket服务器可管理500,000至1,000,000个并发连接。对于5000万个并发连接，大约需要50至100台WebSocket服务器。将用户到服务器的映射存储在Redis中，以便任何实例都能处理重新连接。

**负载均衡**：对WebSocket流量使用第4层负载均衡和最少连接算法。中等规模下，粘性会话是一个务实的起点；对于更高规模，将会话状态外部化到Redis，以便任何服务器都能处理任何重新连接的客户端。

---

### 5 结论

本文介绍了高并发实时消息系统中用于WebSocket压缩的PreparedMessage缓存优化技术。该优化通过缓存压缩后的WebSocket帧并在多个连接中重复使用，消除了冗余的压缩操作。基准测试结果表明，在高并发级别下，广播延迟最多降低4倍，内存分配减少90%以上。

结合Redis Pub/Sub跨节点通信和外部会话状态管理等架构模式，这些优化使WebSocket服务器能够高效处理数十万至数百万个并发连接，同时保持低延迟和可控的资源消耗。

该优化已投入生产使用，可作为Go语言的centrifugal/centrifuge开源库的一部分获取。
